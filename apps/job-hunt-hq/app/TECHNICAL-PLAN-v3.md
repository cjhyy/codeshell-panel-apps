# Job Hunt HQ 3.0 技术方案

状态：已实现并完成自动化验收<br>
更新：2026-08-11

## 1. 产品目标

Job Hunt HQ 3.0 要成为一个以当前项目为唯一数据源的本地求职工作台，而不是把多个
Session 包装成页面。用户必须能够在 Panel 内完成核心动作：

1. 保存和筛选完整 JD；
2. 维护有证据的 Base Resume，并为目标 JD 审核岗位版本差异；
3. 从长期题库开始单题或整场练习；
4. 直接语音或文字回答，保存、评分、优化和重练；
5. 从真实面试结果回流题库、简历事实和补强计划。

Session / Agent 是异步分析能力，不是用户必须理解的导航层。Trace 只负责内部审计，不能成为
Panel 内已有回答写回评分的前置条件。

## 2. 对标结论

调研基于 2026-08-11 可访问的产品说明：

- Exponent 将流程收敛为随时开始、语音回答、即时评分、事后查看转写与 rubric；
- Yoodli 允许按岗位和题目练习，在同一练习中生成动态追问，并在结束后查看分析；
- Big Interview 把 STAR Answer Builder、保存修改和模拟录制串成连续流程；
- Huntr 把 Base Resume、目标 JD、岗位版本和逐项接受/拒绝 AI 修改放在同一求职数据系统中。

参考：

- https://www.tryexponent.com/practice/ai-mock-interviews
- https://support.yoodli.ai/en/articles/9550465-practice-with-yoodli
- https://support.biginterview.com/en/article/the-answer-builder-17twbwl/
- https://huntr.co/product/resume-tailor

Job Hunt HQ 不复制这些产品的云端账户模型，而是采用其成熟交互原则：即时进入、反馈可操作、
历史可比较、修改可撤销，再结合 CodeShell 的本地项目、证据 Source 和 Agent 工具。

## 3. 当前证据与主要问题

2026-08-11 对实际项目 `job-hunt-panel.json` 的只读审计显示：

- 23 道长期题目：15 道 ready、8 道 inbox；
- 8 道 inbox 均只缺 competency，可安全推断后由用户确认；
- 仅 1 次回答和 1 次评分；
- 2 场各 15 题的模拟已放弃且没有回答。

因此题量不是瓶颈。主要流失点是开始成本、旧题整理、长场次恢复和评分等待。此前
`get_job_search_context` 的全量读取还暴露了一个架构问题：业务数据库可以很大，但每次 Agent
调用必须是小而精确的查询。

## 4. 信息架构

### 4.1 一级工作区

保留六个业务工作区，但每个工作区只突出一个当前动作：

| 工作区   | 默认动作         | 次级能力                       |
| -------- | ---------------- | ------------------------------ |
| 岗位池   | 处理下一个 JD    | 筛选、投递阶段、公司情报       |
| 数据源   | 修复一个资料缺口 | JD inbox、Repo、经历、同步状态 |
| 公司情报 | 更新当前目标岗位 | 来源、面经、风险、联系人       |
| 简历版本 | 完成当前简历步骤 | Base、岗位版本、证据、PDF      |
| 面试训练 | 立即练一道       | 今日队列、题库、整场模拟、复盘 |
| 进度     | 推进一个后续动作 | 投递、面试、Offer、复盘        |

### 4.2 面试训练

默认页面顺序：

1. **继续上次**：恢复未结束且有回答的场次；无可恢复场次时隐藏；
2. **今日练习**：弱项、到期复习、目标 JD 高频能力；
3. **快速开始**：随机单题、10 分钟练习、整场模拟；
4. **最近反馈**：最近一次得分、最弱维度、优化稿、再答一次；
5. **题单与长期题库**：作为管理能力下沉，不阻塞开始。

题目页保持全窗口焦点模式。保存回答后原地显示评分状态；评分完成后同时显示 rubric、证据缺口、
可口述优化稿和“再答一次”。用户可以先进入下一题，评分异步完成后写回当前项目。

### 4.3 简历

简历保持四层：事实与证据 → Base Resume → JD Variant → 投递文件。3.0 增加岗位版本差异审核：

- 每条建议包含 `before`、`after`、`reason`、`job_requirement_refs`、`source_refs`；
- 每条建议可接受、编辑或忽略；
- 接受后生成新 revision，不覆盖 Base；
- 无 Source 的建议只能进入“待补事实”，不能写入公开简历。

## 5. 数据架构

### 5.1 唯一数据源

当前项目是业务数据库：

```text
job-hunt-panel.json                 # 小项目完整快照；大项目为索引
career-data/panel-shards/<gen>/     # 受索引保护的 A/B 分片
career-data/jd/                     # 原始 JD 与导入收据
career-data/resumes/                # 公开简历、PDF、证据账本
```

Panel 本地 storage 只保存 UI 偏好和有上限的执行记录。业务实体不能只存在于 WebView storage。

### 5.2 读取契约

任何 Agent 读取都遵守“summary → index → exact record”：

```text
get_job_search_context(scope=summary)
get_job_search_context(scope=questions, status, search, cursor, limit)
get_job_search_context(scope=practice, bank_question_id, practice_attempt_id?)
get_job_search_context(scope=job, job_id)
get_job_search_context(scope=resume, resume_id)
```

禁止把全量 `questionBank`、全部回答历史、完整简历和所有 JD 同时放进一次工具结果。列表只返回摘要；
单题查询只返回该题、指定回答、最近评分和与目标岗位相关的证据摘要。

所有列表均返回 `total`、`cursor`、`limit`、`nextCursor`。所有精确写入使用稳定业务 ID 和 revision；
Panel 内已保存回答的评分以 `practice_attempt_id` 为幂等键，可在原 Trace 丢失时建立恢复 Trace。

### 5.3 练习数据模型增量

调度状态从题目的 attempts / reviews 确定性派生，不把第二份易失效状态写进项目快照。运行时投影为：

```json
{
  "learningState": "unseen | awaiting_review | weak | developing | strong",
  "nextReviewAt": "ISO-8601",
  "reviewIntervalDays": 0,
  "weakDimensions": ["evidence", "depth"],
  "lastScore": 74
}
```

第一次答题但尚未评分时三天后再练；低于 60 分间隔一天，60–69 分间隔两天，70–79 分间隔
四天，80 分以上从十天开始，并根据连续评分逐步增长、最长 45 天。最终 mastered 状态仍由用户
确认；显式“再答一次”不受调度限制。

### 5.4 冲突与恢复

- 写入前使用宿主 revision / modifiedAt 做乐观并发控制；
- 分片先写备用 generation，根索引最后切换；
- Panel 可见时定期只检查根 revision，外部变化时提示重新读取；
- 保留最近一次有效 generation，失败不能覆盖可读取数据；
- UI 明确显示“已保存 / 等待保存 / 外部已更新 / 读取失败”。

## 6. Agent 与评分契约

评分请求必须带：题目 ID、题干、练习回答 ID、回答正文、rubric、目标岗位 ID（如有）、Source
摘要。Prompt 中把回答放在数据标签内，明确它不是指令。

评分输出固定为：

- evidence、structure、depth、relevance 四项整数分；
- strengths 最多 5 项；
- improvements 最多 3 项且按优先级；
- optimizedAnswer 为 60–120 秒可直接口述的完整答案；
- followUp 为下一道动态追问；
- 缺少事实统一写成 `【待确认：…】`，不得编造。

动态追问默认只生成并展示，不自动污染长期题库；用户练习或保存后才进入 inbox。

## 7. 迁移

3.0 启动时执行幂等迁移：

1. 对仅缺 competency 的 inbox 题生成可预览的 fallback；
2. 用户点击“修复并确认”后批量转 ready；
3. 为历史题派生学习状态和下一复习时间；
4. 仅保留有回答的 in-progress 场次作为“继续上次”；零回答场次归入历史，不占首页；
5. 不修改题干、回答、评分、Source 或用户笔记。

## 8. 验收指标

- 新用户从打开面试训练到输入第一段回答不超过 2 次点击；
- 有 ready 题时绝不能显示“0 道题可用”；
- 单题练习不创建整场 mock session；
- 保存回答后立即落项目，Agent 不可用也不丢回答；
- 单题评分只读取精确题目和回答，工具结果稳定小于 64 KiB；
- 23 道题、40 次回答、20 次评分的 fixture 不触发上下文超限；
- 外部修改根快照时 Panel 不静默覆盖；
- Base 和 JD Variant 的每项 AI 修改均可单独接受、忽略和追溯 Source。

## 9. 实施顺序

1. 3.0a：按需上下文工具、题库健康度、旧题批量修复；
2. 3.0b：今日练习、继续上次、随机单题和 10 分钟模式；
3. 3.0c：即时评分状态、重练、动态追问与能力趋势；
4. 3.0d：简历岗位版本差异审核和 revision；
5. 3.0e：项目 revision 监听、冲突提示、恢复入口；
6. 每阶段均通过静态模型测试、真实 Electron E2E 和视觉验收后再安装。

当前 3.0a–3.0e 已落地。3.0e 使用上次成功读取的 revision / modifiedAt 作为写入前提，而不是
临时读取最新 revision 后覆盖；面板可见时每 15 秒及重新聚焦时检查根快照。外部更新发生且
本地干净时自动重新读取，本地已有修改时停止写入并保留当前编辑，由用户明确决定是否放弃本次
修改后重载。真实 Electron E2E 会在延迟保存窗口内注入外部文件更新，并断言外部标记未被覆盖。
题库学习状态与下一次复习时间由练习历史确定性派生，不增加需要人工维护的第二份状态：低于
60 分间隔 1 天、60–69 分 2 天、70–79 分 4 天、80 分以上从 10 天开始随连续评分增长，最长
45 天；立即重答仍由最近反馈入口显式触发。
专注答题区根据题型显示四步结构提示，并以中文约 220 字 / 分钟、英文约 145 词 / 分钟估算
口述时长。未提交回答只在 Panel 本地存储保留一份、最多 6000 字并绑定题目与模拟场次；正式
保存成功后立即清理。Electron E2E 会在只输入草稿、不保存项目的情况下重载整个 WebView，
然后断言同题草稿恢复，避免把内存态误当成可靠恢复。
回答写入项目后，焦点和视口会直接落到“回答已保存 → AI 评分 → 优化重练”三步状态条；评分按钮
明确显示将处理当前题号的这次已保存回答。评分运行、失败重试和结果完成分别占用不同状态，避免
用户保存后继续寻找评分入口，或把后台执行误判为卡死。
同题出现第二次回答后，反馈区增加容量受控的最近练习历史：按真实时间列出第几次、输入方式、
回答摘要、是否评分、当前分数和相对上一份已评分回答的变化。重新评分同一回答时只采用最新评分，
不会把一次重评误算成一次新的回答进步。
岗位版差异现在具备“保留、恢复 Base、编辑后采用”三种动作。每条变化把
`jobRequirementRefs`（为什么要改）与 `sourceRefs`（凭什么能这样写）分开展示；JD 关联由目标岗位
原文与变化要点确定性匹配，无法明确匹配时直接提示未关联，不用模糊的“更符合岗位”代替证据。
内联编辑只替换当前岗位版中的目标要点，沿用已有 Source 映射并记录 `userEdited`；项目写入失败时
回滚岗位版和版本历史，归档 Base 始终保持不变。每次保留、恢复、编辑或批量确认都会创建新的
`versionId`，并记录 `parentVersionId` 与 `revisionReason`；上一版留在版本库，可打开、比较或从旧版
继续派生。正文未变化的纯确认可以沿用有效 PDF，正文变化的修订会清空当前修订的 PDF 导出记录。
直接进入完整简历编辑器时也遵循同一约束：本次编辑的第一次实际文字变更先自动分叉 revision，
之后继续自动保存到这个新修订；离开再进入编辑器时，下一次实际改动再创建新的可回退节点。
项目限流重试期间会显示具体重试次数和“文字仍保留”，不再表现成无状态卡死。
项目写入还会保留加载时的业务内容指纹：根 revision 未变化且业务内容相同的保存请求直接成功返回，
不刷新 `job-hunt-panel.json`；大项目也不会为了比较内容而重新读取全部分片。创建整场或 10 分钟
模拟时，答题框会等场次记录成功写入项目后才启用，失败则回滚场次，避免“界面已开始、项目未落库”。
历史恢复只要求规范题目仍存在于长期题库，不再强依赖原题单；零回答场次不占“继续上次”，新空场
退出时自动清理，旧空场可在历史中移除。
答题页增加按需展开的项目参考稿；它和评分后的优化稿都可以进入一个新的可编辑草稿。已有回答会先
分叉成新练习，不覆盖原回答、原评分或能力趋势。
整套面试上下文也使用独立的 64 KiB 执行预算：每页最多返回 5 道完整题，岗位只返回索引字段，
公司面试情报与候选人证据按当前页题目的 Source 做容量受控摘要。Agent 可用 `nextCursor` 继续读取，
不再因为一套 15 题同时携带完整 Repo、经历和公司调研而接近宿主上限。2026-08-11 对正式项目的
只读验收结果为：15 题拆成 3 页，分别约 26.0、25.5、25.1 KiB；单题练习约 13.6 KiB。
题目从待整理变为可练习、标记掌握、模拟场次创建、结束、停止和空场移除都遵循“项目先确认”的
事务边界；写入失败时回滚 UI，而不是留下只在当前内存中成立的状态。评分写回也在项目成功保存后
才发布 Trace 产物，失败会恢复题目、场次、分数和当前答题状态。完整模拟允许连续作答，结束后的
历史卡片会显示仍待评分的回答数量，并按精确 `practice_attempt_id` 逐题继续评分。
简历页把结构化数据库保存与交付文件导出分开表达：正文、证据和版本链自动保存，并在标题栏显示
“等待同步 / 正在保存 / 已保存 / 外部更新待处理”；显式按钮仅负责“导出 Markdown + 证据”或 PDF。
Agent 新简历和事实 QA 写回失败时恢复原简历、版本、岗位状态和选择；Trace 产物只在项目成功后发布。
PDF 文件已生成但导出收据未同步时保留真实文件并报告部分成功，不再误报为全部完成。
简历手动正文另有一份最多 50,000 字的本地恢复草稿，只用于覆盖项目自动保存前的短窗口；它绑定
当前 revision 与父 revision，Panel 重载后只有版本关系仍匹配才会恢复，并立即再次写入项目。
项目写入成功或业务内容已一致后才清理草稿；用户在冲突提示中明确选择放弃本地修改时则先清理，
不会让自动恢复反悔用户的决定。真实 Electron E2E 会在 500 ms 自动保存前重载 WebView，并断言
恢复正文最终进入项目快照。
面试和简历草稿还各保留一份受容量限制、项目分区隔离的同步恢复副本，避免宿主调用限额恰好阻塞
异步本地缓存。项目快照仍是正式业务数据源；副本只在未提交窗口生效，正式写入成功后立即删除。
项目初始化的 workspace info/list/read 与分片读取也会对瞬时限流执行有上限的指数退避；因此高频操作
后重载不会停在空白数据或“首次写回后创建”。每笔写入只可清理该笔实际保存的 resume 草稿，不能用
完成回调时更新过的内存状态误判后一笔输入已同步。
所有会改变业务实体的 Agent 工具现在采用同一提交边界：先保存完整旧状态，更新内存，等待项目写入，
失败时恢复旧状态，成功后才发布 Trace 产物。该约束覆盖候选人资料、JD 收件箱、岗位导入、投递进度、
公司调研、题库、场次、准备计划、真实面试复盘、简历及私有 QA。面板直接进行的岗位筛选、投递进度、
照片、样式和删除也遵守同一规则；因此“界面显示成功”现在等价于项目主库已经确认写入。
任务没有写回最终结果时，JD 收件箱和渠道验证会从“处理中”收敛到可重试状态，并确认该回退
已进入项目；回退写入失败时明确告警，不再静默留下一条重开后仍显示“处理中”的记录。
候选人基础资料也不再只能等 Agent 同步：姓名、目标角色、联系方式、求职方向和职业简介可以在数据源页直接修正。
该操作同样以项目写入为成功边界；写入失败时恢复 profile、简历与版本链，成功时才让受影响的旧 PDF 进入
“待更新”状态。

CodeShell 宿主同时把 Panel App 和内置浏览器的 WebView 就绪作为硬边界：`getWebContentsId`
只能在 Electron 发出 `dom-ready` 之后读取，重绑也只允许使用已就绪的 guest。另外，已注册的 Panel App
代码和资源可以直接读取，只有凭据形状文件、越界链接和写操作仍保留安全确认。

资料编辑与面试专注区还采用标准可恢复交互：资料有未保存变化时显示明确状态，切页或重载前提示，
保存进行中禁止误切页面；面试对话框锁定键盘焦点，关闭后把焦点还给启动按钮，评分、草稿和语音状态
通过读屏状态区播报。

## 10. 验收结果

| 验收项 | 结果 |

## 11. 非目标

- 不为了“像数据库”而把透明、可版本管理的项目数据立即换成 SQLite；
- 不继续堆积通用题目；

- 不用无法核验的指标美化简历或优化回答。
