# 自然语言设计与可运行原型：Figma 研究及 Design Studio 方案

日期：2026-10-18。状态：研究与技术方案；以下新协议、Skill 调整和原型能力尚未实现。

这是[面板重构方案](design-studio-agent-data-workbench-2026-10-18.md)的交互能力补充。目标包含自然语言改视觉、改页面流、改状态及复杂交互，让用户在设计稿中看到并运行 UI/UX。只把固定转换功能移到 Skill，或者只提供静态画布，都不能满足目标。

## 1. Figma 公开能力给出的参考

下表仅依据官方产品与帮助文档，核对时间为 2026-10-18；不推测闭源模型、规划器或内部事务实现。

| 官方证据 | 值得借鉴的边界 |
| --- | --- |
| Make 接收自然语言及设计上下文，生成代码并展示可交互预览；之后可继续对话、编辑预览或源码。[Create a Figma Make file](https://help.figma.com/hc/en-us/articles/31304485164695-Create-a-Figma-Make-file) | AI 编写运行内容，面板提供上下文和实际预览；固定 HTML exporter 并非必要 |
| Design agent 能根据选区和设计系统编辑画布、组件和布局，可撤销；其支持表仍将传统原型/交互创建标为 “Coming soon”。[Work with the Figma agent](https://help.figma.com/hc/en-us/articles/37998629035799-Work-with-the-Figma-agent-in-design-files) | 自然语言编辑 native 设计与代码原型是不同能力，不能混称已支持任意原型连线 |
| 独立的 Make interactions with AI 可为选中 frames 生成页面流、返回及导航连接，用户能预览、保留或逐条修改。[Make interactions with AI](https://help.figma.com/hc/en-us/articles/24004778051479-Make-interactions-with-AI) | AI 写出的交互应该是设计中可见、可编辑、可运行的数据 |
| 设计原型可用变量驱动文字、可见性等属性，使用表达式、条件和多动作。[Use variables in prototypes](https://help.figma.com/hc/en-us/articles/14506587589399-Use-variables-in-prototypes) | UX 超过页面跳转，需要状态、条件和视觉绑定 |
| Code layers 是画布上的运行代码原型，支持自然语言修改和实际播放，官方标为逐步开放的公开测试。[Code layers in Figma Design](https://help.figma.com/hc/en-us/articles/44193259600535-Code-layers-in-Figma-Design) | 复杂交互可以由代码承载，并作为设计工作内容，而不只作为最后的导出物 |
| Figma 的 custom skills 用 Markdown 封装可复用的 Agent 指引和工作惯例。[Create and manage custom skills](https://help.figma.com/hc/en-us/articles/40283639496599-Create-and-manage-custom-skills-in-Figma) | Skill 适合表达设计方法、团队规范和操作知识；渲染、交互执行与持久化仍需真实工具 |

我们的推导：采用 **Skill + 可编辑设计数据 + 通用交互运行时 + AI 编写的可运行原型**。保留视觉编辑和可检查的页面流，同时给复杂 UX 留下代码表达空间，不追求靠越来越长的 action 列表穷尽全部交互。

## 2. 本地已经有什么，缺什么

代码基线为 Panel Apps `db37b886`，Design Studio 0.22.0。

| 范围 | 已有事实 | 缺口 |
| --- | --- | --- |
| 自然语言改视觉 | `use_design` 可事务修改节点、页面、布局，支持版本核对和撤销 | 提交 prompt 强制固定流程，需要中性化 |
| 交互数据 | `.prototype.json` v1 支持一个全局起始页、click→navigate/back/open-url 和入口断点 | 每图层仅一个 click；没有通用状态、条件、输入、弹层、变体及滚动策略 |
| 面板内播放 | 现有预览按钮通过 HTML iframe 实际播放，无需下载 | 依赖固定 frontend exporter，与 CanvasKit 编辑画布分离 |
| 原型保存 | `createPrototypeStore` 已有 scope 校验、来源引用检查和 sidecar CAS | 独立于主文件，不是跨文件原子事务；未保存原型草稿仅存 UI 内存 Map |
| AI 原型操作 | 生成 HTML 时会消费已保存原型数据 | manifest、CLI 和 `use_design` 均没有原型读写协议，context 也不返回它 |
| UI 状态 | 有编辑器并发版本 `stateRevision` | 它不是用户界面的选中态、loading 或错误态，不能混用 |

证据：[prototype.mjs](../../apps/design-studio/app/prototype.mjs) 95–141 行模型与 247–373 行存储；[prototype-ui.mjs](../../apps/design-studio/app/prototype-ui.mjs) 61–78 行编辑 UI、451–457 行 iframe 预览；[app.js](../../apps/design-studio/app/app.js) 7380 行操作白名单和 8818 行上下文读取；[panel.json](../../apps/design-studio/.codeshell-panel/panel.json) 与 [CLI](../../apps/design-studio/app/tools/design-studio.mjs) 的实际操作表。

因此，首期应让现有原型能力能够被自然语言操控，保留播放入口；随后补齐交互状态与代码原型。不能以增加一个 Skill 文本文件宣称完成。

## 3. 推荐结构及权威数据

| 内容 | 权威表示 | 面板如何体现 |
| --- | --- | --- |
| native 页面、节点、样式、布局 | 现有 v3 设计文档 | 画布与属性编辑，继续可选中、可修改 |
| 页面流、事件、条件、常用状态及绑定 | 版本化 prototype sidecar | 流程连接、热点、交互属性、状态预览与运行 |
| 复杂控件或完整代码视图 | AI 在项目中编写的源码及依赖 | 原型视图，后续可作为画布中的体验区域；默认截图和索引为派生数据 |
| 状态场景 | prototype 中的命名场景与初始化数据 | 场景列表，例如默认、空态、加载、失败、移动端；可初始化并实际交互 |
| 运行时状态 | 一次播放会话的内存状态 | 当前页、历史、输入、弹层、焦点、滚动及变量观察器；重置不改源稿 |

同一个节点事件只允许一个执行 owner：通用交互图或代码。跨边界交互通过明确事件契约传递，不同时执行两套导航。native 几何不能自动覆盖代码布局；代码截图不能冒充 native 可编辑图层。用户要求修改代码视图时，AI 读取源码并修改源码；需要改变 native 设计时，AI 显式提交设计事务。

主 v3 schema 严格拒绝未知字段，继续保持；交互扩展使用 prototype v2，不把 `interactions`、`variables` 或代码直接塞进现有节点。v1 导入转为等价的 click 连接和入口数据，旧文件不在读取时自动覆盖。未知的新能力在旧版本应明确不可编辑，不能静默丢弃后重存。

## 4. 通用交互模型与复杂代码的分界

通用模型表达的是 UI 关系：

```text
flow：入口 screen + 初始状态 + viewport
interaction：source node + trigger + guard? + actions[] + transition?
binding：运行变量/状态 → 可见性、文字或可引用的视觉状态
scenario：初始状态 + 模拟数据/响应 + viewport + 可检查的预期状态
```

先覆盖导航/返回、弹层、滚动、局部状态和绑定；常用 trigger 包括 click、输入变化、focus/blur 和键盘事件。条件与表达式采用有限、可类型检查的数据结构，求值不能把 notes 或任意字符串当 JS。导航历史、返回位置、overlay stack 和变量生命周期由通用解释器定义，具体业务流程由 AI 写进文档。

视觉状态必须有真实内容：展开区、错误提示、loading、菜单、弹层、组件替换等都引用存在的节点、画板或代码视图。组件 variant 目前没有原生完整模型，初期可显式引用替代子树/页面；正式的 variant schema 需单独定义，不能把实例的 `componentId` 当作已实现的变体系统。

播放器的基础求值契约是：

```text
(designSnapshot, prototypeSnapshot, runtimeState, event)
    → nextRuntimeState + visualProjection + effects
```

点击播放不改源设计，不因按钮叫“登录”就默认登录，也不因页面叫“详情”就自动路由。静态设计数据与输入状态求值得到可渲染场景；画布截图需记录所选场景和状态，不能只截默认态。

模型表达不了的内容，交给 AI 写原型代码：复杂表单、拖拽排序、图表/地图、自定义文本编辑、动态列表、异步竞态等。面板提供代码原型引用、运行及观察协议，不为这些业务分别增加动作。代码原型属于交互设计工作本身，目标框架由 AI 和项目决定，面板不执行 v3→固定 HTML 的生成。

代码引用应绑定项目内 source entry、内容/依赖摘要及可用场景。项目已有工具负责构建与启动，先使用现有浏览器预览能力；画布内嵌体验区域作为后续适配。CanvasKit 本身不执行 DOM，内嵌代码需要独立的浏览器表面、选中/运行模式和坐标组合，不能只添加一个字段就宣称完成。

预览区分 `live` 开发模式与 `frozen` 快照模式。普通 dev server/HMR 属于 live，只报告实际观察到的运行代次，变化后旧结果失效，不声称它对应精确源码快照。frozen 模式需要把构建产物及全部传递资源发布为不可变对象并从该快照加载，或加载时重验、变化即拒绝；仅记录源码 hash 并不能证明浏览器运行的是那组字节。

运行代码的预览上下文不持有编辑器 Host bridge，源码不能由编辑器 `eval`。父层只接受约定的 ready、选择锚点、场景和观察消息，不暴露任意 Host 调用。此处是原型运行机制，实际项目实现仍使用正常开发工具。

## 5. AI 操作协议与 Skill

复用已有工具名处理视觉部分，补充下面的领域接口。以下名称与字段是拟定契约，实施时同步更新 manifest、CLI、Runtime Skill 与能力发现。

| 入口 | 数据/操作 | 版本要求 |
| --- | --- | --- |
| `get_design_context` | 原有节点/组件/素材；按需 include 原型摘要和状态场景 | 主设计与请求附件的组合版本，标识截断 |
| `get_design_prototype` | 按 flow、node 或 scenario 读取连接、状态、绑定及代码引用 | 返回设计版本、prototype 文件 revision 与原型草稿版本 |
| `update_design_prototype` | upsert/remove flow、interaction、state/binding、scenario、code reference 等通用事务；v1 首期仅开放现有字段 | 校验 `expected_state_revision`、`expected_prototype_revision`、`expected_prototype_draft_revision`；返回影响范围和诊断 |
| `preview_design_prototype` | 启动/重置一个场景、派发受支持事件、读取状态与运行截图；不是任意脚本执行接口 | runtime ID、live/frozen 模式及运行代次；frozen 才给精确 snapshot ID；变化使旧预览过期 |

旧工具 16 个，移除四个固定交付工具后为 12 个；加素材读取 1 个与上述三个原型工具后仍为 16 个。上下文沿用原工具，不再为每种业务扩一个工具。CLI 提供对应的已保存原型读写/校验；不能声称关闭面板后已有浏览器播放能力，需按实际运行环境发现。

现有主文件 revision 不覆盖 sidecar，主画布版本也不覆盖原型编辑窗口的内存草稿。首期为草稿增加独立 epoch，原型工具与 UI 走同一更新队列；人工改过草稿后，旧 Agent 事务应冲突。主设计和原型分步提交时返回每步回执，不宣称跨文件原子性。

frozen 预览以完整 snapshot 绑定：设计版本、prototype 版本、不可变运行产物与依赖/资源摘要及场景。发布时先准备所有引用对象并校验，再提交最后的引用清单，从该清单服务运行内容；不能仍然加载可变开发目录。这保证预览不选择半份内容，不等于已有源文件具备跨文件原子事务。回执丢失先查询和核对，不重复执行旧写入。

撤销也分层实现：native 修改沿用设计历史；prototype 修改新增草稿 history，持久 sidecar 回退用当前 revision 做 CAS 补偿；代码修改由源文件变更回执记录各文件的前后摘要。跨层修改记录复合 receipt，撤销前逐层检查后继版本，人工已继续修改则报冲突并保留，不强行恢复。复合撤销完成前，UI 只展示各层实际可用的回退入口，不把 native 的 Ctrl-Z 宣称为全部原型代码的撤销。

**Skill 推荐演进现有 `design-studio:repo-design`，不另做固定原型生成器。** 主体内容为：

1. 触发范围：自然语言创建、修改或解释设计与交互；遵守用户本次范围，解释任务走只读。
2. 数据约定：稳定 ID、坐标与布局、组件/素材引用、交互 owner、场景和各自版本。
3. 按需读取：先定位所选内容，再读取相关视觉、状态和连接；复杂行为读取原型源码。
4. 修改方式：视觉走设计事务；常用 UI 关系走原型事务；超出通用模型时修改原型代码。不规定框架，不强制固定输出文件。
5. 验证方式：按用户这次改变的行为进行真实输入/点击/键盘测试，并检查相关状态截图；未运行的部分明确说明。
6. 冲突与恢复：版本过期重新读取，保留人工改动，核对保存和预览回执。

团队的设计规范、可访问性检查和 UX 评审可作为可选 Skill 或项目规则。默认 Skill 不强制每次 PRD→设计→生成→对比，也不要求所有 warning 清零；工具及 runtime 没有的能力不能靠 Skill 文案伪造。

## 6. 用户怎样看到 UI/UX 进入设计稿

编辑器保留三个相通的视图：视觉编辑、原型连接、运行。选择元素后可以直接输入要求；AI 返回的修改在原位置更新，可查看影响范围，并使用该层已实现的撤销/变更回执继续编辑。

以用户要求“点卡片进详情，返回保留位置；提交失败保留输入并允许重试”为例：

| 用户意图 | AI 实际修改 | 用户核对的位置 |
| --- | --- | --- |
| 卡片进入详情 | 给真实卡片节点添加指向详情页的连接，显式定义导航数据 | 连接视图与实际点击结果 |
| 返回保留位置 | 指定返回历史及滚动恢复策略 | 列表先滚动，再进入详情并返回 |
| 输入与提交 | 定义字段状态、输入反馈、提交触发；复杂表单由原型代码实现 | 运行态实际输入，不只切换两张截图 |
| loading/失败/重试 | 创建可见 loading/error 内容、保留输入规则及模拟响应场景 | loading、失败、重试场景和状态观察器 |
| 调整体验 | 用户继续说“错误提示移到字段下面”或“移动端换成底部弹层” | AI 修改真实设计/代码，重新运行场景，按变更层提供回退回执 |

上述只是验收样例，面板不内置该流程。改成预约、文件浏览或教学引导时，只变化设计数据与 AI 代码。场景记录模拟响应时应明确模拟，不把原型成功视为真实后端或账号操作成功。

## 7. 实施与完成条件

| 阶段 | 实施内容 | 必须看到的证据 |
| --- | --- | --- |
| A：接通自然语言原型 | 中性化 prompt/Skill；增加原型读取、v1 事务与运行接口；共享 UI 草稿版本；保留当前 iframe 播放 | 自然语言增改实际页面连接，画布可检查、预览可点击、人工并发会冲突；只读不保存 |
| B：状态与可运行内容 | 状态/事件/绑定/场景；代码原型引用及独立预览；版本化截图与错误观察 | 多状态 UI、复杂交互能实际运行，AI 继续修改内容，无需增业务动作；当前代码表面与 native 内容区分明确 |
| C：运行时和保存统一 | 共享场景渲染；CLI 按需读写；冻结运行闭包、复合回执及包含代码/场景的备份 | live/headless 能力按实测声明；重开和完整恢复后仍可运行同一场景 |

A 只证明现有导航打通；B、C 仍是目标内工作，不能把 A 当成完整 UI/UX 能力交付。代码原型无需等通用交互图覆盖所有场景再开始支持，避免为复杂 UX 继续扩大固定动作集。

实现验收矩阵：

| 要求 | 应有证据 |
| --- | --- |
| 自然语言修改视觉 | 修改前后设计节点/布局 diff，实际画布截图，撤销回到原版本 |
| 页面跳转与返回 | 真实点击，当前页/历史/返回位置记录；更换页面和节点 ID 后仍按数据运行 |
| 条件与多种 UI 状态 | 两条条件分支实测，默认/hover/focus/disabled/error/empty/loading 等相关状态可重现 |
| 弹层和输入体验 | 实际打开/关闭、焦点与键盘行为；表单失败保留输入，重试有结果 |
| 复杂交互不靠业务枚举 | 至少一个拖拽/动态列表或其他自定义原型由 AI 源码实现，再用自然语言修改并实测 |
| 响应式 | 指定桌面和手机视口运行，核对导航、布局和弹层，不能只检查初始页面断点 |
| 可编辑、可继续演进 | 连接和场景可以手工修改；代码视图修改回到源码；没有虚构自动无损双向转换 |
| 数据与并发 | 主稿、原型草稿、sidecar、代码版本分别核对；旧事务拒绝，预览过期可识别；分层/复合撤销不覆盖后续人工改动 |
| 保存与恢复 | 关闭、重开及恢复备份后，资源、交互、代码、场景齐全且可播放；frozen 携带完整运行闭包。源码备份明确依赖安装、构建与运行环境前提，不冒充可直接运行快照 |
| 无固定转换依赖 | 不调用 import_html/generate_frontend/compare_frontend/read_product_brief；不为新业务添加面板分支 |

本轮只核对资料、审查现状和完成方案修订，没有实现上述新工具、交互模型或 Skill，也没有把文档检查视为产品验收。
