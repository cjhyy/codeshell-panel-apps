## 1. 两个断口的具体位置

数据源：真实 Host R1 的原始裁图 `.tmp/cross-surface-lh-evidence/crops-1x/cs-r1__100d__cjk-skip-ink__{gpu,browser}.png`（zoom 1，DPR2，裁图列 = 9.2 + 2 × 字符 advance）。追踪数据在 `.tmp/cjk-skip-gap-fix-evidence/trace/`。

| 断口 | 字符与 cluster | GPU 缺口左边界 | HTML 缺口左边界 | 字形墨迹左边缘（band 下方 alpha） | 模型 round(l − th)，th = 3.6 |
| --- | --- | --- | --- | --- | --- |
| A | "gyp" 中 `y` 之后的 `p`（U+0070，竖笔在第 135–136 列） | 131 | 132 | 134.95（第 134 列 alpha 0.03） | round(131.35) = 131 |
| B | "jump" 中 `m` 之后的 `p`（U+0070，竖笔在第 345–346 列） | 341 | 342 | 344.95 | round(341.35) = 341 |

- 两个缺口的右边界（竖笔之后）完全一致。
- 下划线所在行是 47–50（第 47 行约 0.2，第 48–49 行满，第 50 行约 0.3）。
- 这次运行是单个 run、单一颜色、同一字体（Inter，按资源字节注册）。因此 run 区间裁切、前缀测量的 kerning、颜色边界都不适用。
- `j` 与中文相邻处的缺口（[278,283]、[288,291]）完全一致；CJK 字符正确地不开缺口。
- 字体别名的测量顺序风险已由隔离测试覆盖：browser 路由使用的是独立的 FontFace。
- **差异的本质：** HTML 在竖笔前留 3 列空白（132–134 / 342–344），GPU 留 4 列（131–134 / 341–344）。要让 GPU 也落在 132 / 342，需要墨迹左边缘 ≥ 135.1（或 345.1），或者膨胀量 ≤ 3.45。也就是要在 0.15 px 以内分辨字形边缘位置，而 8 位栅格的抗锯齿外溢（第 134 列 alpha 0.03）本身就有这么大。

## 3. 方向性观察（真实 Host，Chromium 130）

同一次 R1 中所有 skip-ink 用例里有差异的缺口边界（`trace/r1-cases-boundaries.txt`）：

- `underline-descender-2line` 第 1 行：两个缺口右边界，GPU 比 HTML 早 1 列；
- `cjk-skip-ink`：上表两个左边界，GPU 早 1 列；另外行尾 GPU 364、HTML 365。

所有差异都是 **GPU 比 HTML 偏左 1 列**；`node-underline-mixed` 的 36 个边界没有差异。而 Chromium 148 上误差正负平衡、没有系统偏移（见第 2 节）。

这一系统方向**可能**是 Chromium 130 与 148 在截线或吸附上的差异，但只能在真实 Host（Electron 33 / Chromium 130）上标定。离线没有 Chromium 130，也没有离线改善作为依据，所以按约定不启动真实运行。即使标定，得到的也是特定 Chromium 版本的参数，不是通用规则。

## 4. 无法还原的原因，以及需要什么平台能力

- Blink 的 skip-ink 是用 Skia 在设备坐标下，对实际排版后的字形轮廓求精确截线（`getIntercepts`），使用 Chromium 当时版本的字体后端（mac 上为 CoreText 栅格与 hinting）。
- 我们只能从 Canvas2D 栅格的 alpha 反推：8 位量化加抗锯齿外溢，边缘精度大约 ±0.1–0.2 px。这在 Chromium 148 上就有约 20% 的边缘相差 ±1 列。
- CanvasKit 的 FreeType 轮廓加默认 opsz 实例也不等于 Chromium 的字形。
- Canvas2D 和 DOM 都没有提供截线 API。
- 要精确一致，至少需要以下之一：
  1. 由浏览器自己把带下划线的文字绘制进 canvas（例如 HTML-in-Canvas 一类的能力；Electron 33 正式版不具备）；
  2. 由 Host 提供原生文字截线；按本批约束，不新增 Host 接口；
  3. 在 Chromium 130 上标定版本专用参数（需要真实运行，而且不通用）。
